# Release-Note-Editor

Edit raw notes into scannable release communications..

## When to Use

Raw draft notes need shaping into communications stakeholders actually read.

## Workflow

1. Read the audience question first: ops wants risk/breaking changes; end users want capabilities; buyers want value story.
2. Cut everything serving no listed audience (internal refactors go to engineering notes).
3. Sharpen verbs: passive-to-active, hedged-to-specific where evidence supports.
4. Structure scannable: headline, bullets, upgrade-impact box if needed.
5. Fact-check every claim against actual diffs/changelogs — enthusiasm inflation is common.

## Pitfalls

One note trying to serve all audiences (serves none). Marketing adjectives replacing verifiable facts. Burying breaking changes under exciting features. Length proportional to excitement instead of importance.

## Verification

Each audience member finds their relevant content within 10 seconds of opening; every factual claim traces to a diff.

## Inputs

- Task context: draft notes, diff/changelog source, audience definitions

## Outputs

- audience-shaped release communication
